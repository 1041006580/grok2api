# 上游全量吸收但保持本地稳定的集成设计

## 背景

当前本地仓库与 `upstream/main` 已经明显分叉：

- 本地相对 `upstream/main` 领先 `48` 个提交
- 本地相对 `upstream/main` 落后 `66` 个提交
- 两边共同基线为 `d76b5e4`
- 在隔离 worktree 中试合并 `upstream/main` 时，产生了 `42` 个冲突

冲突热点主要集中在：

- `app/services/reverse/`
- `app/services/grok/services/video.py`
- `app/services/token/`
- `app/core/config.py`
- `config.defaults.toml`
- `_public/static/...` 与 `app/static/...` 的目录迁移
- `app/api/v1/admin_api -> app/api/v1/admin`
- `app/api/v1/public_api -> app/api/v1/function`

这说明问题不是“补几个提交”，而是“本地长期定制 + 上游结构重构”的叠加集成。

## 已统一的本地合同基线

为避免后续测试把错误接口当成基线，执行计划统一以下当前本地真实合同：

- 核心视频创建接口为 `/v1/videos`
- 文件代理接口为 `/v1/files/image/{filename:path}` 与 `/v1/files/video/{filename:path}`
- 配置访问以 `app.core.config.config` 单例和 `get_config()` 为基准，不使用不存在的 `settings` 对象
- `public_api` 与 `public` 页面仍是当前行为基线；引入 `function` 命名时必须通过兼容层保持旧行为可用

## 已观测的冲突分组

基于暂停式试合并得到的首轮冲突分组如下：

- `app/services/reverse/`: `15`
- `_public/static/admin/`: `6`
- `app/api/v1/`: `5`
- `_public/static/common/`: `3`
- `app/services/token/`: `3`
- `_public/static/function/`: `2`
- `app/services/grok/`: `2`
- 单文件冲突：`.gitignore`、`app/api/pages/`、`app/core/config.py`、`config.defaults.toml`、`docker-compose.yml`、`uv.lock`

以上分组已在 Task 2 中按当前执行基线重新验证，结果保持一致。

## 用户确认的设计约束

本次集成采用以下硬约束：

1. 以本地当前行为和稳定性为基准，不主动替换现有稳定业务逻辑
2. 全量吸收上游的目录形态、模块结构、配置面和新增入口
3. 当上游实现与本地实现冲突时：
   - 默认保留本地行为
   - 默认吸收上游结构
   - 只有在单独确认时才允许以“上游行为”覆盖“本地行为”
4. 整个过程必须可停、可验、可退，不能一次性在主工作区直接硬并

## 目标

### 主目标

在不破坏本地现有功能的前提下，将仓库整体形态尽量对齐 `upstream/main`，并把上游新增能力入口集成进当前项目。

### 成功标准

- 本地现有聊天、图片、视频、文件代理、后台管理、Token 管理能力不退化
- 上游的目录重构、模块命名调整、静态资源归位、配置扩展全部吸收或建立明确兼容层
- 上游新增能力入口并入当前项目，但默认不改变本地既有行为
- 集成完成后仓库中不存在长期半迁移状态和不可解释的临时补丁

### 非目标

- 不追求重写成本极高的历史清理
- 不追求把本地 46 个提交“重放”到上游历史之上
- 不在第一轮集成中顺手做额外功能重构

## 方案对比

### 方案 1：直接整包合并并一次性解完冲突

优点：

- 操作路径最短

缺点：

- 风险最高
- `reverse`、`video`、`token`、`config` 等热点会同时进入不稳定状态
- 一旦验证失败，很难定位是哪一层引入了行为退化

结论：不采用。

### 方案 2：分层全吸收，结构先行，行为后校准

优点：

- 满足“全量吸收上游”目标
- 能把“上游结构”与“本地行为”分开处理
- 每一层都有独立验证点和回滚点

缺点：

- 节奏比一次性合并慢
- 需要先补一层基础回归验证能力

结论：采用。

### 方案 3：以上游为底重放本地提交

优点：

- 理论上历史更整洁

缺点：

- 成本最高
- 需要拆解本地 46 个提交的依赖关系
- 对当前这类多热点分叉仓库不现实

结论：不采用。

## 总体架构

本次集成采用“上游结构优先、本地行为优先”的双轴策略：

- 形态目标：向 `upstream/main` 对齐
- 运行语义：以本地当前 `main` 为基线

冲突解决分三类：

### 1. 保留本地行为

适用范围：

- 请求重试与限流
- 反向代理容错
- 视频生成与扩展逻辑
- Token 调度与状态机
- 媒体缓存/存储的本地稳定策略

原则：

- 保留当前稳定实现
- 只在接口层和结构层对齐上游，不主动改业务语义

### 2. 采用上游结构

适用范围：

- `_public` 静态资源布局
- `admin_api -> admin`
- `public_api -> function`
- 页面与静态模板的目录组织
- 上游新增的目录和模块边界

原则：

- 尽量落到上游命名和目录布局
- 必要时保留薄兼容层，避免一次性切断旧入口

### 3. 组合实现

适用范围：

- 上游新增入口或配置项需要进入当前项目
- 但底层实现必须落到本地稳定逻辑上

原则：

- 上游给“入口”和“结构”
- 本地给“行为”和“兜底”

## 分层执行顺序

### 第一层：结构迁移层

目标：

- 吸收目录改名与文件归位
- 先把仓库骨架对齐上游

典型范围：

- `_public/static/...`
- `app/api/pages/`
- `app/api/v1/admin/`
- `app/api/v1/function/`

策略：

- 优先接受上游目录形态
- 为本地旧引用保留短期兼容导入或路径转发

### 第二层：配置与启动层

目标：

- 合并上游新增配置面
- 保持本地默认行为不变

典型范围：

- `app/core/config.py`
- `config.defaults.toml`
- `docker-compose.yml`
- `main.py`
- `pyproject.toml`

策略：

- 配置采用并集
- 新配置项默认必须是非侵入式
- 启动链路必须继续支持当前本地运行方式：`uv sync` + `uv run main.py`

### 第三层：API 与页面层

目标：

- 对齐上游路由组织方式
- 保持本地接口行为不退化

典型范围：

- `app/api/pages/admin.py`
- `app/api/v1/video.py`
- `app/api/v1/function/video.py`
- 管理后台页面入口

策略：

- 先保留旧路径可访问
- 再把内部实现切到新结构

### 第四层：核心服务层

目标：

- 解最关键、最容易破坏稳定性的冲突

典型范围：

- `app/services/reverse/*.py`
- `app/services/grok/services/video.py`
- `app/services/token/*.py`

策略：

- 严格按模块分批处理，不混修
- 先解 `reverse`
- 再解 `video`
- 最后解 `token`

### 第五层：前端与静态资源层

目标：

- 吸收上游页面布局、静态资源归位和新增前端入口

典型范围：

- `_public/static/admin/...`
- `_public/static/common/...`
- `_public/static/function/...`

策略：

- 对齐上游目录布局
- 保持本地现有交互行为不退化

### 第六层：文档、CI、锁文件收尾层

目标：

- 吸收非核心但必须完成的上游改动

典型范围：

- `.github/...`
- `readme.md`
- `docs/README.en.md`
- `uv.lock`

策略：

- 最后处理，避免让非核心变更干扰主功能验证

## 兼容层设计

兼容层只允许是“薄兼容”，不允许形成双实现长期并存。

允许的兼容方式：

- 旧 import 转发到新模块
- 旧页面入口转发到新路径
- 旧静态资源引用映射到 `_public`
- 旧配置字段继续可读，新字段可选生效

不允许的兼容方式：

- 复制两份核心业务逻辑长期共存
- 在多个模块中分散写临时判断
- 不可定位、不可删除的“历史包袱 if/else”

## 验证策略

当前仓库没有现成的稳定回归套件，且当前环境中 `pytest` 不在 PATH。为避免盲并，执行前必须先补一层最小回归能力。

### 验证分级

#### 1. 启动验证

- `uv sync`
- `uv run main.py`
- 确认应用能启动、路由能注册、关键页面可打开

#### 2. 代码健康验证

- 针对热点模块补最小回归测试
- 至少覆盖配置加载、路由存在性、关键导入链和核心接口契约

#### 3. 冒烟验证

至少覆盖：

- `/v1/chat/completions`
- `/v1/images/generations`
- 视频生成/扩展相关入口
- `/v1/files`
- `/admin`
- Token 管理与配置写入入口

### 准入规则

- 一层未过，不进入下一层
- 一个热点模块未稳定，不进入下一个热点模块
- 每一层结束都必须形成独立提交点

## 回滚策略

### 小回滚

回退当前层最近一次检查点提交。

### 中回滚

仅回退当前热点模块合并，不动前面已验证完成的层。

### 大回滚

直接丢弃集成 worktree 分支，主工作区保持不变。

## 实施建议

1. 在隔离 worktree 中创建正式集成分支
2. 先补回归验证能力
3. 再在该分支中执行暂停式合并并分层解冲突
4. 每层完成后立即验证并提交
5. 收尾后再考虑是否清理兼容层

## 验收标准

集成完成后必须同时满足以下条件：

- 本地既有功能行为与当前稳定版本一致
- 上游目录结构和模块命名基本吸收完成
- 上游新增入口已并入仓库
- 热点模块没有残留未解释的冲突式修补
- 仓库可维护性优于当前“长期分叉”状态
